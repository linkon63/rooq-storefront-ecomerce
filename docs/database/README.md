Names here are the real Postgres names (`@@map` / `@map`), so they are snake_case. In TypeScript the same things are camelCase model fields.

## Conventions

- **Ids** are UUID v7 strings (`@default(uuid(7))`), generated by the Prisma client. They are time-ordered, so new rows land at the end of the B-tree index instead of at random pages. Join tables use a composite primary key instead.
- **Names** are snake_case in the database (`@@map` / `@map`). Every table has `created_at` (default `now()`); mutable tables have `updated_at`, set by Prisma on every write.
- **Money** is `decimal(12,2)` (taka with poisha); quantities are `integer`. Mappers turn `Decimal` into numbers in API responses.
- **Every foreign key is indexed**, and every relation states its `ON DELETE` behaviour explicitly (see [Delete behaviour](#delete-behaviour)).
- **Soft deletes** where history matters: `users.deleted_at`, `products.archived_at`, `product_variants.is_active = false`. Orders, returns and the stock ledger point at these rows, so they are never hard-deleted once used.
- **Snapshots:** `order_items` and `order_addresses` copy names, SKU, colour, size, prices and address at purchase time.
- **Enums:** enums kept from the earlier version of the app keep their lowercase values, which the UI already sends (`pending`, `cash_on_delivery`). Enums added for the fashion domain are UPPER_SNAKE (`TRUE_TO_SIZE`).
- **Images** live only in `media` (+ `media_blobs`). No other table has an image URL column.

How the domains connect, in one paragraph: **users** own carts, wishlists, addresses, orders, reviews, returns and notifications. A **product** belongs to a brand and a category, has many **variants** (colour × size) and an ordered gallery of **media**. Carts, orders, reviews, back-in-stock requests, returns and stock movements all point at the **variant** (the SKU), not the product. An **order** has one frozen address, many lines, payments, shipments and status logs. A **return** points at the order and at the specific order lines, and its stock effects go through **stock_movements**. Every image anywhere is a row in **media**.

## Media and binary images

Images are stored **as bytes inside Postgres** (no S3, nothing written to `public/`). That makes the app fully stateless, so it runs on Vercel's serverless functions without a file system or an object store, and a database backup includes every image.

### Two tables, on purpose

| Table | Holds | Why it is separate |
| --- | --- | --- |
| `media` | Metadata: `kind`, `provider`, `mime_type`, `width`, `height`, `size_bytes`, `checksum`, `alt`, `external_url`, `uploaded_by_id` | Small and cheap to join. Product lists, cards and admin tables join it to build image URLs and `<img>` dimensions. |
| `media_blobs` | `data bytea`: the encoded image | Large. Keeping the bytes in their own table (1:1, `media_id` is both PK and FK, ON DELETE CASCADE) means `include: { media: true }` can never drag megabytes into a list query. The bytes are read by **exactly one query**: `getMediaForServing()` in `lib/server/media/queries.ts`. Everything else selects `mediaRefSelect` (`id, provider, externalUrl, alt, width, height`). |

`provider` is `DATABASE` (bytes in `media_blobs`) or `EXTERNAL` (a URL we do not host: videos, Google profile pictures, embeds). Videos are never stored in the database.

### Every image is a foreign key

The earlier schema mixed approaches: a `media` table with `s3` / `cloudinary` / `local` URLs, plus free-text URL columns (`categories.image_url`, `brands.logo_url`, `news.cover_image_url`, `settings.logo` / `icon` / `favicon`, `users.avatar`) and a JSON array of image URLs per campaign. The same picture could exist in three places, and deleting one left broken links. Now every image is a `media` row, referenced by FK:

| Single image (FK column, ON DELETE SET NULL) | Ordered galleries (join table, ON DELETE CASCADE) |
| --- | --- |
| `users.avatar_media_id`, `categories.image_media_id`, `brands.logo_media_id`, `collections.cover_media_id`, `collection_looks.media_id`, `news.cover_media_id`, `order_items.image_media_id`, `settings.logo_media_id` / `icon_media_id` / `favicon_media_id` / `youtube_thumb_media_id` | `product_media` (per-colour product gallery with `position`, `is_primary`, `color_id`), `review_media` (customer photos), `campaign_media` (banner images) |

The API still answers with the string fields the UI expects (`imageUrl`, `logoUrl`, `coverImageUrl`, `avatar`, `url`). Mappers build them with `mediaSrc(media)` from `utils/media-url.ts`: `/api/v1/media/<id>` for DATABASE, the stored URL for EXTERNAL.

### Upload pipeline

1. `POST /api/v1/upload` (staff only) or a module endpoint that accepts multipart (product gallery, review photos) receives the file.
2. `assertImageFile()` rejects anything over **5 MB** or not JPEG / PNG / WebP / AVIF / GIF (`lib/constants/media.ts`). Messages come from `ERROR_MESSAGES.media`.
3. `processImage()` (sharp) applies EXIF rotation, caps the long edge at **1600 px** (never enlarges), strips metadata and re-encodes to **WebP quality 80**. A 3–5 MB phone photo typically ends up around 100–250 KB.
4. `saveImage()` hashes the result (sha256). If a DATABASE row with the same `checksum` exists it is **reused** (deduplication); otherwise it inserts `media` + `media_blobs` in one nested write. `UNIQUE (checksum, provider)` makes this safe under concurrent uploads: the loser of the race gets a `P2002` and re-reads the winner's row.
5. The caller stores the returned id in the FK column (`logo_media_id`, a `product_media` row, …). When a client sends back a URL from step 1, `mediaIdFromUrl()` turns it into the id again.

### Serving and caching

`GET /api/v1/media/[id]` (public):

- answers the bytes with the stored `Content-Type`, `Content-Length` and `X-Content-Type-Options: nosniff`;
- sends `Cache-Control: public, max-age=31536000, immutable` and `ETag: "<checksum>"`. An id's bytes never change (a new image gets a new id), so browsers can keep it for a year. Vercel's CDN caches function responses only when they also carry `s-maxage` or `CDN-Cache-Control` (see [deployment](../deployment.md#media-caching));
- answers `304 Not Modified` when `If-None-Match` matches;
- redirects (302) to `external_url` for EXTERNAL media; answers 404 for unknown ids.

`next/image` accepts these paths through `images.localPatterns` in `next.config.ts`, so the optimiser can still resize per viewport on top.

### Deleting images

Removing an image from a gallery deletes only the join row. Deleting a `media` row deletes its blob by cascade. **Note:** every foreign key that points at `media` is SET NULL or CASCADE, so Postgres never refuses to delete a media row that is still in use. Because identical uploads are deduplicated, one row may be shared by several owners. Code that frees an image must check that nothing else references it before deleting it; it cannot rely on an FK error. The one helper for this is `releaseMedia(ids, tx?)` in `lib/server/media/release.ts`, which counts references across all 14 relations and deletes only orphans.

### Trade-offs to keep in mind

- The database grows with the catalogue: roughly 150 KB per image after processing. `pg_dump` and backups grow too.
- Each image costs a function invocation and a database read whenever it is not already cached by the browser, the CDN or the `next/image` optimiser. Edge caching (`s-maxage`) matters on Vercel.
- If image volume ever outgrows the database, only `media_blobs` and the serve route need to change: switch `provider` to a new value and keep every FK as it is.

## Identity & Access

Who can sign in and what they may do. Customers and staff share `users`; the role decides the rest (`superadmin` passes every check, `admin` runs the panel, `user` is a shopper). Users are soft-deleted with `deleted_at`, so the cascades below rarely fire in practice.

### `roles`

Named roles that the API guards match on (`superadmin`, `admin`, `user`). *(Prisma model `Role`.)*

**Key columns:** `name` (unique, the guard key), `is_system` (protected roles cannot be deleted in the admin panel).

| Relationship | Cardinality | ON DELETE | Why |

**Keys and indexes:** PK (`id`) · UNIQUE (`name`)

## Inventory

Stock is held on `product_variants.stock` (the running balance). Every change also appends one row to `stock_movements` in the same transaction, so the balance can always be explained. Shoppers can ask to be told when a sold-out size returns.

### `stock_movements`

Append-only stock ledger. One row per change; `product_variants.stock` is the running balance. *(Prisma model `StockMovement`.)*

**Key columns:** `type` (INITIAL, RESTOCK, SALE, RETURN, EXCHANGE, CANCELLATION, ADJUSTMENT, CORRECTION), signed `quantity`, `stock_after`, `reason`; optional links to the order, return request and staff user that caused it.

| Relationship | Cardinality | ON DELETE | Why |
| --- | --- | --- | --- |
| `variant_id` → [`product_variants`](#product_variants) | N:1 (required) | RESTRICT | The SKU whose stock changed. RESTRICT: a variant with ledger history cannot be hard-deleted; it is archived (`is_active = false`). |
| `order_id` → [`orders`](#orders) | N:1 (optional) | SET NULL | The order that caused a SALE / CANCELLATION movement. |
| `return_request_id` → [`return_requests`](#return_requests) | N:1 (optional) | SET NULL | The return that caused a RETURN / EXCHANGE movement. |
| `created_by_id` → [`users`](#users) | N:1 (optional) | SET NULL | Staff member who made a manual adjustment. |

**Keys and indexes:** PK (`id`) · INDEX (`variant_id`, `created_at`) · INDEX (`order_id`) · INDEX (`return_request_id`) · INDEX (`created_by_id`) · INDEX (`type`, `created_at`)

### `back_in_stock_requests`

"Notify me when my size is back" sign-ups, guest or signed in. *(Prisma model `BackInStockRequest`.)*

## Optimisations in this schema

- Bytes are split from metadata (`media_blobs`), so no list query ever reads image data.
- Composite indexes match the hot queries: `products (status, archived_at)` for the shop listing, `product_variants (product_id, is_active)`, `product_media (product_id, color_id, position)` for colour galleries, `reviews (product_id, status, created_at)`, `orders (user_id, placed_at)` and `(status, placed_at)`, `stock_movements (variant_id, created_at)`, `notifications (user_id, is_read, created_at)`, `collections (type, is_active, position)`.
- Denormalised aggregates on `products` (`sold_count`, `rating_avg`, `rating_count`) make "popular" and "top rated" sorts index scans instead of aggregations. Services update them in the same transaction as the order or review.
- Uniques enforce business rules in the database: one review per user per product, one cart per user, one variant per colour × size, one back-in-stock request per variant and e-mail, one social link per platform, one return item per order line per request.
- Stock is a running balance plus an append-only ledger, so the balance is O(1) to read and every change remains explainable.

When `prisma/schema.prisma` changes (new migration), regenerate `rooq-erd.drawio` and `schema.dbml` and update this README in the same change. After editing, check the files with:

```bash
xmllint --noout docs/database/rooq-erd.drawio
npx -y -p @dbml/cli dbml2sql docs/database/schema.dbml --postgres > /dev/null
```
